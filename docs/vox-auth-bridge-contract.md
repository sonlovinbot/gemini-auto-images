# VOX ↔ Auto ChatGPT Images Auth and Bridge Contract

## Document status

- Status: **Proposed — requires product and security approval**
- Contract revision: `0.1`
- Automation protocol: `vox-chatgpt/1`
- Applies to: Auto ChatGPT Images extension and VOX STYLE VIDEO
- Runtime implementation authorized: **No**
- Last updated: 2026-07-29

This document freezes the intended connection boundary before either runtime is
changed. It does not authorize a VOX authentication migration or a production
deployment.

## Decision summary

VOX and the extension support two deliberately separate connection modes:

1. **Local development**
   - Allowed only for loopback origins (`localhost` and `127.0.0.1`).
   - Keeps the current no-login bridge available behind a development flag.
   - Must never be enabled for a remotely reachable deployment.
2. **Production**
   - Uses OAuth Authorization Code with PKCE `S256`.
   - Uses `chrome.identity.launchWebAuthFlow()` and a redirect generated by
     `chrome.identity.getRedirectURL()`.
   - Treats the extension as a public client. No client secret is embedded in
     the extension.
   - Uses short-lived, audience-restricted access tokens and rotating,
     revocable refresh tokens.

The page bridge is only a wake-up and intent channel. It must never transport
VOX tokens, ChatGPT credentials, image bytes, data URLs, refresh tokens, or
project secrets.

## Normative language

The terms **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** describe
contract requirements. They become binding only after this proposal is
approved.

## Goals

- Let a user explicitly connect an extension installation to a VOX account and
  workspace.
- Let VOX start an authorized batch without exposing credentials to the web
  page or ChatGPT.
- Restrict the extension to the minimum batch-execution permissions.
- Preserve the current working local flow during migration.
- Make disconnect, revocation, lease expiry, retry, and recovery deterministic.
- Keep VOX authoritative for batches, tasks, returned assets, and idempotency.

## Non-goals

- Moving all VOX projects from browser `localStorage` to a cloud database.
- Using the user's Chrome or ChatGPT identity as their VOX identity.
- Giving the extension general project-edit, project-delete, billing, or
  account-administration permission.
- Sending a VOX access token through `window.postMessage`.
- Making the extension the permanent owner of batch state or generated assets.
- Supporting arbitrary user-entered VOX API origins in production V1.

## Current-state constraint

VOX projects and storyboards are currently primarily persisted in browser
`localStorage`. The extension batch backend can durably save an image and bind
it to `batchId`, `taskId`, `projectId`, and `beatId`, while the VOX page later
copies that result into the local storyboard.

Until VOX projects become server-owned:

- `projectId` and `beatId` are durable correlation identifiers, not sufficient
  authorization boundaries.
- Authorization MUST be enforced using the batch owner, workspace, connection,
  and task lease.
- A successful result receipt means the server durably stored the asset and its
  task/beat association.
- The VOX page remains responsible for reflecting that result into its local
  storyboard.
- The UI MUST report a local attachment failure separately from a server result
  save failure.

## Trust boundaries

### Trusted components

- VOX authorization server and extension API.
- The Auto ChatGPT Images service worker.
- The VOX same-origin page after its normal VOX login.

### Untrusted or lower-trust components

- `window.postMessage` traffic.
- Content scripts as credential carriers.
- The ChatGPT document and its page scripts.
- Temporary ChatGPT asset URLs.
- User-entered remote origins.
- Batch, project, task, or beat IDs presented without an authorized token.

### Credential placement

- Access and refresh tokens MUST remain in extension-owned execution context.
- Tokens MUST NOT be injected into the VOX document or ChatGPT document.
- Tokens MUST NOT appear in URLs, logs, diagnostics, result metadata, or bridge
  messages.
- The service worker MUST perform authenticated VOX API requests.
- Diagnostic export MUST redact authorization headers and token response bodies.

## Identifiers

| Identifier | Owner | Purpose |
| --- | --- | --- |
| `connectionId` | VOX | Revocable grant connecting one extension installation to a user/workspace. |
| `subjectId` | VOX auth | Stable authenticated VOX user identity. |
| `workspaceId` | VOX | Authorization and data-isolation boundary. |
| `batchId` | VOX | Durable generation batch identity. |
| `taskId` | VOX | Durable task identity. |
| `leaseToken` | VOX | Proves the executor currently owns a task claim. |
| `requestId` | Caller | Correlates bridge and API requests without granting authority. |
| `idempotencyKey` | VOX | Prevents duplicate task-result effects. |
| `installId` | Extension | Random local installation label; never used as VOX user identity. |

All security-sensitive identifiers MUST be generated with a cryptographically
secure random source. IDs alone never grant access.

## Production OAuth client

### Client properties

```text
client_id: auto-chatgpt-images
client_type: public
grant_types:
  - authorization_code
  - refresh_token
response_types:
  - code
pkce_methods:
  - S256
```

The production Chrome Web Store extension ID and redirect URI MUST be
registered explicitly. Development extension IDs MUST use a separate
development client registration and MUST NOT be accepted by the production
client.

### Redirect URI

The extension creates the callback with:

```js
chrome.identity.getRedirectURL("vox")
```

Expected shape:

```text
https://<extension-id>.chromiumapp.org/vox
```

VOX MUST compare the complete redirect URI against the registered allowlist.
Prefix, wildcard, or substring matching is forbidden.

### Authorization request

```http
GET /api/extension/oauth/authorize
  ?response_type=code
  &client_id=auto-chatgpt-images
  &redirect_uri=<exact-registered-redirect>
  &scope=extension.batch.read%20extension.task.execute%20extension.result.write
  &code_challenge=<base64url-sha256>
  &code_challenge_method=S256
  &state=<random-state>
```

Requirements:

- `code_verifier` MUST contain 256 bits of random entropy and satisfy the PKCE
  length and character requirements.
- `S256` is mandatory. `plain` MUST be rejected.
- `state` MUST be generated per authorization attempt and compared exactly.
- The interactive flow MUST start from an explicit user action.
- An authorization code MUST be single-use, bound to the exact client,
  redirect URI, scopes, subject, workspace, and PKCE challenge.
- Authorization code lifetime SHOULD be at most 60 seconds.
- Canceling or closing the flow MUST leave the extension disconnected.

### Consent screen

The VOX authorization page MUST show:

- Current VOX account.
- Selected workspace.
- Extension name and verified publisher.
- Requested permissions in plain language.
- The browser/device label when available.
- Approve and cancel actions.

If the user is not signed in, VOX may ask them to sign in and then return to the
same consent request. VOX MUST NOT silently approve a new extension connection.

### Token exchange

```http
POST /api/extension/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&client_id=auto-chatgpt-images
&code=<single-use-code>
&redirect_uri=<exact-registered-redirect>
&code_verifier=<original-verifier>
```

Example response:

```json
{
  "token_type": "Bearer",
  "access_token": "<opaque-or-signed-token>",
  "expires_in": 900,
  "refresh_token": "<rotating-refresh-token>",
  "refresh_expires_in": 2592000,
  "scope": "extension.batch.read extension.task.execute extension.result.write",
  "audience": "vox-extension-api",
  "connection_id": "con_..."
}
```

Access-token requirements:

- Recommended lifetime: 10–15 minutes.
- Audience MUST be restricted to the VOX extension API.
- Subject, workspace, connection, client, scopes, issued time, and expiry MUST
  be verifiable by the resource server.
- Revoked or disconnected connections MUST be rejected.

Refresh-token requirements:

- Refresh tokens for this public client MUST rotate on every successful use.
- Reuse of an invalidated refresh token MUST revoke the active token family.
- Refresh tokens SHOULD expire after 30 days of inactivity.
- Logout, password reset, account disablement, workspace removal, or explicit
  disconnect MAY revoke all related extension connections.

### Refresh

```http
POST /api/extension/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token
&client_id=auto-chatgpt-images
&refresh_token=<current-refresh-token>
```

The response MUST contain a new access token and a new refresh token.

### Revocation and connection inspection

```text
POST /api/extension/oauth/revoke
GET  /api/extension/connection
```

`GET /connection` returns only display-safe connection metadata:

```json
{
  "connected": true,
  "connectionId": "con_...",
  "accountLabel": "Son",
  "workspaceId": "ws_...",
  "workspaceLabel": "VOX Studio",
  "scopes": [
    "extension.batch.read",
    "extension.task.execute",
    "extension.result.write"
  ]
}
```

Disconnect MUST revoke the server connection and then remove extension-local
tokens and connection metadata. It MUST NOT delete completed VOX assets.

## Scopes

| Scope | Allows | Does not allow |
| --- | --- | --- |
| `extension.batch.read` | Read batches assigned to the authenticated subject/workspace. | List unrelated projects or other users' batches. |
| `extension.task.execute` | Claim tasks and report progress, failure, pause, or cancel for a valid lease. | Edit prompts, beat identity, project content, or task ownership. |
| `extension.result.write` | Upload a generated result for a currently leased task. | Upload arbitrary project files or replace a conflicting completed result. |

V1 MUST request all scopes together because they form one executor capability.
Future adapters may split them further.

## Page bridge

### Envelope

VOX to extension:

```json
{
  "source": "vox-style-video",
  "protocol": "vox-chatgpt/1",
  "type": "CHECK_CONNECTION",
  "requestId": "uuid",
  "payload": {}
}
```

Extension to VOX:

```json
{
  "source": "auto-chatgpt-images",
  "protocol": "vox-chatgpt/1",
  "type": "CHECK_CONNECTION_RESULT",
  "requestId": "uuid",
  "ok": true,
  "data": {}
}
```

### Validation

The bridge MUST:

- Require `event.source === window`.
- Require exact `event.origin === location.origin`.
- Require an allowlisted VOX origin.
- Require the exact protocol major version.
- Validate the message type and payload schema.
- Generate a response for the same `requestId`.
- Reject messages from frames, arbitrary sites, and unsupported origins.
- Never trust a `connectionId`, account, workspace, or token supplied by the
  page.

### Message types

#### `CHECK_EXTENSION`

Returns:

```json
{
  "installed": true,
  "extensionVersion": "0.4.0",
  "protocol": "vox-chatgpt/1"
}
```

#### `CHECK_CONNECTION`

Input:

```json
{
  "apiOrigin": "https://vox.example.com"
}
```

Output:

```json
{
  "connected": true,
  "apiOrigin": "https://vox.example.com",
  "accountLabel": "Son",
  "workspaceLabel": "VOX Studio",
  "scopes": [
    "extension.batch.read",
    "extension.task.execute",
    "extension.result.write"
  ]
}
```

This response is display-only and grants no authority to the page.

#### `OPEN_CONNECTION_PANEL`

May be sent only from a user gesture. It asks the extension to open its side
panel in a connection state. The side panel owns the actual **Connect VOX**
button that starts the interactive auth flow.

#### `START_CHATGPT_BATCH`

Input:

```json
{
  "batchId": "uuid",
  "apiOrigin": "https://vox.example.com"
}
```

Rules:

- The message MUST NOT contain tasks, tokens, reference bytes, or result URLs.
- The extension MUST use its stored connection matching `apiOrigin`.
- The extension MUST fetch the batch from VOX and verify ownership.
- The extension MUST reject a batch outside the token subject/workspace.
- Repeating this message for the same non-terminal batch is a reconnect, not a
  request to duplicate tasks.

## Generate button flow

1. VOX sends `CHECK_EXTENSION`.
2. If absent, VOX shows install/reload guidance without creating a batch.
3. VOX sends `CHECK_CONNECTION`.
4. If disconnected, VOX sends `OPEN_CONNECTION_PANEL`.
5. The user connects VOX from the extension side panel.
6. VOX observes `connected` and creates the batch through its authenticated
   same-origin web session.
7. VOX sends `START_CHATGPT_BATCH` with only `batchId` and `apiOrigin`.
8. The extension fetches, validates, and claims the batch.
9. The extension opens or reuses ChatGPT and begins sequential execution.

VOX MAY retain a short-lived pending "Generate with ChatGPT" UI intent while
authorization completes. It MUST NOT store tokens in that intent.

## Extension API authorization

Production requests from the service worker include:

```http
Authorization: Bearer <access-token>
X-Vox-Extension-Protocol: vox-chatgpt/1
X-Vox-Connection-Id: con_...
X-Vox-Request-Id: <uuid>
```

Task-mutating calls additionally include:

```http
X-Vox-Task-Lease: <lease-token>
```

The server MUST derive subject and workspace from the validated token. It MUST
NOT accept them from request JSON as authority.

### Batch ownership

Every production batch record adds:

```json
{
  "subjectId": "usr_...",
  "workspaceId": "ws_...",
  "connectionId": "con_..."
}
```

The web session creating a batch and the extension connection claiming it MUST
belong to the same allowed subject/workspace. `projectId` is not an
authorization boundary.

### Claim response

```json
{
  "batch": {
    "batchId": "...",
    "revision": 4
  },
  "task": {
    "taskId": "...",
    "revision": 2,
    "lease": {
      "token": "<opaque-lease-token>",
      "expiresAt": "2026-07-29T13:00:00.000Z"
    }
  }
}
```

Only a hash of the lease token SHOULD be stored server-side. A task-mutating
request with a missing, expired, or mismatched lease MUST return
`409 CLAIM_CONFLICT` or `412 STALE_TASK_REVISION`.

Progress updates SHOULD include the last observed task revision. A successful
progress request renews the lease and returns the new revision and expiry.

## Reference descriptors

Production batches SHOULD use server-owned asset descriptors:

```json
{
  "id": "ref_...",
  "name": "character.png",
  "mimeType": "image/png",
  "byteLength": 1945820,
  "checksum": "sha256-hex",
  "order": 0,
  "downloadPath": "/api/extension/assets/ref_..."
}
```

Requirements:

- Production batches MUST NOT contain `data:` reference URLs.
- Reference order MUST be explicit and immutable for the attempt.
- The service worker downloads each asset using the VOX access token.
- Bytes MUST be validated against MIME type, size limit, and checksum.
- The validated bytes SHOULD be stored temporarily in extension IndexedDB.
- ChatGPT receives image bytes, never the VOX token.
- Missing or invalid required references block prompt submission.

Local development MAY temporarily accept existing loopback URLs or data URLs,
but this behavior MUST be disabled in production.

## Result submission and receipt

The extension sends actual image bytes as multipart data plus:

```json
{
  "protocol": "vox-chatgpt/1",
  "batchId": "...",
  "taskId": "...",
  "projectId": "...",
  "beatId": "...",
  "attempt": 1,
  "taskRevision": 8,
  "idempotencyKey": "...",
  "expectedOutputName": "B01-chatgpt.png",
  "checksum": "sha256-hex",
  "mimeType": "image/png",
  "byteLength": 2182340,
  "width": 941,
  "height": 1672
}
```

Successful response:

```json
{
  "saved": true,
  "duplicate": false,
  "receiptId": "rcp_...",
  "batchId": "...",
  "taskId": "...",
  "projectId": "...",
  "beatId": "...",
  "assetId": "asset_...",
  "checksum": "sha256-hex",
  "taskRevision": 9,
  "associationMode": "batch_task_identity",
  "savedAt": "2026-07-29T13:10:00.000Z"
}
```

The extension marks a task completed only after receiving a valid receipt whose
task, beat, idempotency key, and checksum match the attempted result.

Repeated delivery with the same idempotency key and checksum MUST return the
existing receipt with `duplicate: true`. The same idempotency key with a
different checksum MUST return `409 RESULT_CONFLICT`.

`associationMode` values:

- `batch_task_identity`: current transitional mode; the server durably binds
  the asset to task and beat IDs, then the VOX page reflects it into the local
  storyboard.
- `server_storyboard`: future mode; VOX also durably updates a server-owned
  storyboard before returning success.

## Error contract additions

| Code | HTTP | Meaning |
| --- | ---: | --- |
| `VOX_AUTH_REQUIRED` | 401 | Access token is absent, expired, invalid, or wrong-audience. |
| `VOX_SCOPE_REQUIRED` | 403 | Token lacks the required executor scope. |
| `VOX_CONNECTION_REVOKED` | 401 | The connection was disconnected or revoked. |
| `VOX_WORKSPACE_FORBIDDEN` | 403 | Batch is outside the authorized workspace. |
| `OAUTH_STATE_MISMATCH` | n/a | Extension callback state does not match the pending request. |
| `OAUTH_CODE_EXCHANGE_FAILED` | n/a | Authorization code could not be exchanged safely. |
| `CLAIM_CONFLICT` | 409 | Another executor owns the task lease. |
| `STALE_TASK_REVISION` | 412 | Caller is updating an older task revision. |
| `REFERENCE_ASSET_INVALID` | 422 | Reference bytes do not match their descriptor. |
| `RESULT_CONFLICT` | 409 | Same idempotency key was used with different result bytes. |
| `RESULT_SAVE_UNCONFIRMED` | 502 | No valid durable-save receipt was returned. |
| `LOCAL_STORYBOARD_ATTACH_FAILED` | n/a | VOX saved the result but the local page could not reflect it into its storyboard. |

OAuth errors MUST follow the standard OAuth `error` and `error_description`
shape. User-facing messages MUST not expose tokens or server internals.

## CORS and host permissions

Production:

- VOX MUST return CORS headers only for the registered production
  `chrome-extension://<extension-id>` origin.
- `Access-Control-Allow-Credentials` is not required for bearer-token API calls.
- The authorization page uses the normal VOX web origin and session cookie.
- The extension manifest SHOULD list the single official VOX production origin.
- Custom VOX origins are out of scope for production V1.

Development:

- Loopback origins may be allowlisted explicitly.
- `*` MUST NOT be used once authorization is enabled.
- Production bearer tokens MUST NOT be accepted by a loopback server.

## Extension storage

Persist:

- API origin.
- Connection ID and safe display labels.
- Granted scopes.
- Access-token expiry.
- Current refresh token.
- Pending PKCE state only while authorization is active.
- Active batch/task checkpoints.

Do not persist:

- VOX login password.
- ChatGPT credentials.
- Authorization codes after exchange.
- Expired refresh tokens.
- Raw authorization headers in logs.

Chrome extension storage is not a hardware-backed secret vault. Short token
lifetimes, narrow scopes, rotation, revocation, and bounded diagnostics are
required to limit the impact of local compromise.

## Recovery rules

- Service-worker restart reloads connection metadata and refreshes only when an
  API request requires it.
- An expired access token may be refreshed once, then the original request may
  be retried once with the same `X-Vox-Request-Id`.
- `401 VOX_CONNECTION_REVOKED` stops execution and requires explicit reconnect.
- A lost or expired task lease triggers server reconciliation; it never causes
  blind prompt resubmission.
- If submission evidence exists, the extension first inspects the ChatGPT
  conversation for the existing result.
- Reauthorization must not discard a recoverable local ChatGPT checkpoint.
- A new connection cannot mutate a task claimed by a revoked connection unless
  VOX explicitly reissues the task and a new lease.

## Feature flags and rollout

Suggested server flags:

```text
VOX_EXTENSION_ENABLED
VOX_EXTENSION_AUTH_REQUIRED
VOX_EXTENSION_LOCAL_DEV_ALLOWED
VOX_EXTENSION_ALLOWED_IDS
```

Rules:

- Local development remains the default only in local builds.
- Production requires auth before the first limited release.
- New bridge message types are additive; the existing local
  `START_CHATGPT_BATCH` path remains available during migration.
- Runtime changes are implemented in small, reversible phases after this
  contract and the accompanying test plan are approved.

## Approval gates

The following decisions require explicit approval before runtime code changes:

1. Official production VOX origin.
2. Production Chrome Web Store extension ID.
3. VOX login/session provider and workspace model.
4. Token format and storage backend.
5. Access and refresh token lifetimes.
6. Whether V1 issues refresh tokens or requires periodic interactive reconnect.
7. Local development bypass policy.
8. Maximum reference size and supported MIME types.
9. Transitional `batch_task_identity` receipt semantics.
10. Exact files and migrations permitted in the VOX repository.
